# 流式时序算法实验：444.mp4

## 实验目标

稳定版时序算法需要读完整段视频后才能确认所有 PPT 时间段，因此即使后续
ASR 与 LLM 已经支持并发，第一项云端任务仍然开始得很晚。本实验不更换页面
判定规则，而是让现有时序算法按块持续更新状态，只要前面的页面不再可能被后续
画面改写，就立即确认并提交。

实验分支：`experiment/streaming-temporal-pipeline`

## 实现方法

- 视频仍按稳定版的采样间隔、变化检测、动画合并、边界细化和代表帧选择规则处理。
- 每处理完一个视频块，重新计算当前时序分段。
- 保留最新两个候选段，避免跨块动画或短暂过渡被过早确认为独立页面。
- 更早的稳定前缀立即成为最终页面，提取 1080p 截图并触发 ASR。
- 每页 ASR 完成后立即触发该页 LLM 评分。
- ASR 与 LLM 继续共用最多 5 个云端请求，不增加限流风险。
- 调试模式会校验已经确认的页面不能在后续块中发生变化；如变化则立即报错，
  不会静默生成错误时间段。

单独运行页面检测、不同时运行云端任务时，本实验耗时 131.511 秒，稳定版基准为
156.566 秒；输出仍为 24 页，所有开始和结束时间完全一致。

本次云端 ASR 返回 19,186 个字符，稳定版另一次独立调用返回 19,241 个字符；
24 页中有 15 页文字完全相同。MiMo ASR 和 LLM 的独立请求存在少量非确定性，
所以评分分别为 96.46 和 97.62。这不是页面切分差异：两次运行的时间段、截图、
音频分片数和上传字节数均相同。

## 结论

这个方案比“双算法并跑”更值得继续：

- 它没有第二套检测器，不会重复解码整段视频。
- 它保留了已经验证过的时序算法判定结果，没有引入阈值算法的漏页风险。
- 它解决的是等待结构：第 1 页在约 14 秒时开始 ASR，而不是等待整段检测完成。
- 444.mp4 的全链路实际提速 33.5%，并且没有增加上传量或云端并发。

建议先不要合并到稳定版；继续在片头重复、长时间静止、快速翻页和大量动画的
代表视频上回归。如果这些视频仍保持页面边界一致，再接入 GUI 并作为默认流程。
